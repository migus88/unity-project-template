# csharp-ls (C# language server for the LSP tool)

Claude Code's built-in `LSP` tool gets C# support from the official
`csharp-lsp@claude-plugins-official` plugin, which launches the `csharp-ls` binary. The
plugin is already enabled for everyone in `.claude/settings.json`; each machine still needs
the .NET SDK, the `csharp-ls` dotnet tool on `PATH`, and Unity-generated project files.

Why csharp-ls: it's the server Anthropic's official plugin uses, it installs as a
cross-platform dotnet tool, and it loads a `.sln` by itself. Microsoft's Roslyn LSP only
loads projects when the editor sends custom `solution/open` messages, which Claude Code
doesn't send. OmniSharp is in maintenance mode.

## Check
```bash
dotnet --list-sdks                # need a 10.x SDK (csharp-ls 0.28+ targets net10.0)
csharp-ls --version               # Windows: Get-Command csharp-ls
ls src/*.sln                      # exactly one: src/src.sln
claude plugin list                # csharp-lsp@claude-plugins-official ... enabled
ls -la src/.claude                # symlink -> ../.claude (Windows: Get-Item src/.claude)
```

## Install

**1. .NET SDK 10**
- macOS: `brew install --cask dotnet-sdk`, or the pkg from https://dotnet.microsoft.com/download.
  The Homebrew `dotnet@8` formula can come before it on `PATH`. Make sure the `dotnet` that
  runs first lists a 10.x SDK. The official pkg installs to `/usr/local/share/dotnet`.
- Windows: `winget install Microsoft.DotNet.SDK.10`
- Linux: `sudo apt-get install -y dotnet-sdk-10.0` (Ubuntu 24.04+), or
  `curl -sSL https://dot.net/v1/dotnet-install.sh | bash -s -- --channel 10.0` and then set
  `DOTNET_ROOT=$HOME/.dotnet` and add `$HOME/.dotnet` to `PATH`.

**2. csharp-ls**. Run it from a folder with no `.csproj`/`.sln` in it, such as your home folder.
In `src/`, `dotnet tool install` fails with "contains more than one project file".
```bash
cd ~ && dotnet tool install --global csharp-ls      # update later: dotnet tool update --global csharp-ls
```
```powershell
Set-Location $HOME; dotnet tool install --global csharp-ls
```

## Configure

**PATH.** The binary lives in `~/.dotnet/tools` (Windows: `%USERPROFILE%\.dotnet\tools`).
Claude Code only finds it if it's on `PATH` in the shell that starts `claude`.
- macOS: the .NET installer adds a literal `~/.dotnet/tools` to `/etc/paths.d`. Processes that
  aren't shells don't expand `~`, so add this to `~/.zshrc` (or `~/.bashrc`):
  `export PATH="$PATH:$HOME/.dotnet/tools"`
- Linux: add the same line to `~/.bashrc` / `~/.zshrc`.
- Windows: the SDK adds it to the user `PATH` on first run. If `Get-Command csharp-ls` fails, run
  `[Environment]::SetEnvironmentVariable('Path', $env:Path + ";$env:USERPROFILE\.dotnet\tools", 'User')`
  and open a new terminal.

**Project files.** `*.sln` and `*.csproj` are gitignored and generated by Unity. The project
folder is `src/`, so Unity writes `src/src.sln`. Without them csharp-ls has nothing to load.
- Open the project in Unity (Unity 6000.6, see `src/ProjectSettings/ProjectVersion.txt`) with
  an external script editor chosen under *Settings → External Tools* (Rider, Visual Studio or
  VS Code), then click **Regenerate project files**.
- With a live Editor and the Unity CLI you can do the same thing:
  `unity command eval 'Unity.CodeEditor.CodeEditor.CurrentEditor.SyncAll(); return "ok";'`
  (this needs an external editor to be set, and the Editor's main thread must not be busy).
- csharp-ls searches the workspace recursively and loads the **first** `.sln` it finds. If a
  stale extra `.sln` shows up (for example `unity-project-template.sln` from before the
  project moved to `src/`), delete it. Only `src/src.sln` should exist.

**Plugin.** It's already enabled in `.claude/settings.json`. If `claude plugin list` doesn't show it:
```bash
claude plugin install csharp-lsp@claude-plugins-official --scope project
```
Then restart Claude Code (or run `/reload-plugins`) from a shell where `csharp-ls` is on `PATH`.

**`src/.claude` symlink.** Claude Code reads project settings (and so the plugins) only from
`<cwd>/.claude/settings.json`. `src/.claude` is a committed relative symlink to `../.claude`,
so a session started in `src/` gets the same settings; skills are not listed twice (Claude
Code dedupes by real path). Check: `ls -la src/.claude` (macOS/Linux) or
`Get-Item src/.claude | Select-Object LinkType, Target` (Windows) must show a link, not a
plain file. If it's a plain text file containing `../.claude`, git checked the link out
without symlink support (Windows default). Fix:
- macOS / Linux: `rm -f src/.claude && ln -s ../.claude src/.claude`
- Windows, preferred: enable Developer Mode (Settings → System → For developers) or use an
  elevated shell, then `git config core.symlinks true`, delete the file
  (`del src\.claude`) and run `git checkout -- src/.claude`.
- Windows, fallback without admin or Developer Mode: a junction, from `cmd` in the repo root:
  `del src\.claude` then `mklink /J src\.claude "%CD%\.claude"`. `mklink /J` needs an
  absolute target. Git may then report `src/.claude` as modified: don't commit that
  (`git update-index --assume-unchanged src/.claude` hides it).
Without the link, start Claude Code from the repo root (`cd src && claude plugin list`
shows the plugins as disabled).

## Verify
- Ask Claude to call the `LSP` tool with `workspaceSymbol` and query `CoreInstaller`, or with
  `hover` on any type in `src/Assets/_Project/**/*.cs`. The first call can take about 30–60 s
  while the solution loads.
- "No LSP server available for file type: .cs" means the plugin didn't load. Run `/plugin`
  and look at the **Errors** tab. `Executable not found in $PATH` is the PATH step above. If
  `/plugin` doesn't list `csharp-lsp` at all, the session was started outside the repo, or
  in `src/` with a broken `src/.claude` link (see Configure).
- Empty results or unresolved Unity types mean the `.sln`/`.csproj` files are missing, stale,
  or point to a Unity install that isn't on this machine. Regenerate them.
